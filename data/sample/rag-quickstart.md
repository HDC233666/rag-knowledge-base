# RAG 知识库问答（示例知识库）

## 什么是 RAG

RAG 是 Retrieval-Augmented Generation 的缩写，中文叫「检索增强生成」。
一句话解释：先让程序去资料库里查相关内容，再把查到的内容和问题一起交给大模型，让它「开卷答题」。

为什么需要 RAG：

- 大模型的知识有截止日期，不知道你公司内部文档、你的笔记、最新的产品文档；
- 直接问大模型，它可能一本正经地编造答案（幻觉）；
- 把资料检索出来放进上下文，模型就能基于真实材料回答，并且能给出处。

## RAG 的基本流程

1. 导入阶段：把文档切分成小块（chunk），建立索引；
2. 提问阶段：把问题也做同样的处理，去索引里找最相关的几块；
3. 生成阶段：把「相关问题 + 检索到的片段」拼成提示词，交给大模型；
4. 展示阶段：把答案返回给用户，并附上它参考了哪些片段（引用）。

## 文本切分（Chunking）

切分是 RAG 里最影响效果的一步。

- 块太大：检索不准，还会浪费上下文窗口；
- 块太小：一句话被切断，模型看不到完整信息；
- 块之间保留一定重叠（overlap）：可以让跨块的句子被完整读到。

常见的切分策略：按段落切、按句子切、按固定字数切、按语义（用模型判断）切。
最常用的是「按段落 + 固定字数上限 + 重叠」。

## 检索：BM25 与向量检索

BM25 是一种经典的词频统计检索算法，属于「稀疏检索」：

- 关键词命中越多、越稀有，得分越高；
- 不需要训练，速度极快；
- 缺点：不理解同义词，比如「电脑」和「计算机」不会互相命中。

向量检索（稠密检索）用 embedding 模型把文本变成向量：

- 语义相近的句子，向量距离也近；
- 能处理同义词、跨语言；
- 缺点：需要 embedding 模型、向量库，成本更高。

实践中常用「混合检索」：BM25 + 向量检索各取一部分，再合并排序。

## 常见的向量数据库

- FAISS：Facebook 开源，本地库，适合单机；
- Chroma：轻量，适合快速原型；
- Milvus：分布式向量数据库，适合大规模生产；
- Elasticsearch：搜索起家，支持向量检索和全文检索混合；
- Pinecone：云服务，免运维。

## 如何减少幻觉

1. 在提示词里明确要求「资料里没有就说不知道」；
2. 让模型在回答里标注引用编号；
3. 设置相似度阈值，检索不到相关片段时直接回答「没找到」；
4. 对关键结论做二次校验（比如让另一个模型检查）。

## 如何评估 RAG 效果

- 检索层：召回率、命中率、MRR；
- 生成层：答案相关性、忠实度（是否只依据资料）、引用准确性；
- 端到端：人工打分、RAGAS 等自动评估框架。

## 本项目的实现

本项目为了零依赖、开箱即用，选择了：

- 切分：按句子切 + 目标字数 + 重叠；
- 检索：BM25（纯 Python 实现，rank-bm25 库）；
- 生成：调用 DeepSeek 的 chat 接口；
- 存储：JSON 文件，重启不丢数据。

想升级成生产可用：把检索替换成 FAISS/Chroma + embedding 模型，其它部分几乎不用改。
