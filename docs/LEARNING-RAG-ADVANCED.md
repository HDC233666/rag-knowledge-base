# RAG 进阶讲解：从 BM25 到「混合检索 + 重排 + 改写 + 评估」

> 面向零基础。读完你应该能：讲清楚每条链路为什么要加、怎么加、加完怎么证明它有用；面试被追问时能接住。

---

## 0. 先建立一个直觉

RAG = 先查资料，再让大模型看着资料回答。

```
问题 → 检索（找到相关片段）→ 拼上下文 → 大模型生成 → 带引用的回答
```

**检索质量决定 RAG 质量。** 检索没找对片段，大模型再强也只能瞎编。所以 RAG 的升级，本质上是**检索链路的升级**。

---

## 1. 第一代：BM25（词面匹配）

**它是什么**：按「词是否出现、出现几次、这个词有多稀有」给文档打分的老牌算法（搜索引擎最经典的排序算法之一）。

**优点**：
- 毫秒级、零依赖、CPU 就能跑；
- 用户问题里带着原文关键词时，非常准。

**缺点**：
- 只认字面：问「资料更新了模型还在答旧的」，文档写的是「外挂知识库能随时更新」——词不重合，就找不到。
- 中文要分词，同义词、口语表达都吃亏。

**一句话面试版**：BM25 是稀疏检索，靠词频和逆文档频率打分，快而准但不懂语义。

---

## 2. 第二代：向量检索（语义匹配）

**它是什么**：把问题和每个片段都用向量模型（embedding）转成一串数字（向量），再算余弦相似度，谁的向量跟问题最像，谁就最相关。

**为什么能解决词面问题**：向量模型在大量语料上训练过，「资料更新」和「外挂知识库随时更新」在向量空间里距离很近——它比的是**意思**，不是**字面**。

**本项目的选择**：
- 模型 `bge-small-zh-v1.5`：512 维、中文优化、ONNX 推理、**CPU 可跑**，不需要 GPU；
- 不引入 FAISS/Chroma：14 个切片直接 numpy 算余弦就够，少一个依赖少一个坑（数据量大了再换向量库，接口不变）；
- bge 官方建议：**查询侧**加指令前缀（「为这个句子生成表示以用于检索相关文章：」），**文档侧不加**——加错会掉点。

**一句话面试版**：向量检索是稠密检索，把语义压缩成向量后算相似度，能处理同义/改写，但可能丢关键词精确性。

---

## 3. 第三代：混合检索 + RRF 融合

**为什么要混合**：BM25 强在关键词精确，向量强在语义泛化，两者互补。问题是——**它们的分数不能直接相加**（BM25 是几十上百的分，余弦是 0~1）。

**RRF（Reciprocal Rank Fusion）**：不看分数，只看排名：

```
score(d) = Σ  1 / (k + rank_i(d))
```

- `rank_i(d)`：文档 d 在第 i 路结果里的名次（从 1 开始）；
- `k`：平滑常数，论文经验值 60；
- 两路都排前面的片段，得分叠加，自然排到最前。

**为什么用 RRF 而不是加权求和**：不用归一化、不用调权重、对分数尺度不敏感——这也是它成为工业界默认融合方法的原因。

**一句话面试版**：多路召回各自排序，用 RRF 按名次融合，避免分数不可比的问题，实现简单且稳健。

---

## 4. 第四代：LLM 重排（rerank）

**为什么召回之后还要排一次**：召回阶段的目标是「别漏」（宽召回 top-12），排序阶段的目标是「排得准」（精排取前 4）。用大模型逐条判断「这个片段和问题相关吗、能打几分」，比向量相似度更细。

**本项目做法**：让大模型给每个候选打 0–10 分，输出 JSON，按分数取前 4。**输出不合法 JSON 就保留原顺序**（兜底），不因为一次模型抽风把整个服务搞挂。

**代价**：每问一次要多调一次大模型，延迟从毫秒级涨到秒级。所以做成开关（`RAG_ENABLE_RERANK`），评估时对比开/关。

---

## 5. 第五代：查询改写（multi-query）

**问题**：用户问得口语化、信息密度低（「这东西到底咋整」），一次检索容易漏。

**做法**：先让大模型把问题改写成 2–3 个不同角度的检索式，分别召回、各自排序，再用 RRF 融合。本质是「用大模型补齐用户没说的上下文」。

**注意**：改写也可能改跑偏 → 兜底策略是失败/超时就退回原问题；改写结果建议缓存（同一问题反复问不用重复花钱）。

**一句话面试版**：多查询召回——让大模型生成多个检索式并行召回再融合，提升召回率，代价是多一次模型调用。

## 6. 评估：怎么证明升级真的有用

**不做评估 = 自嗨。** 加了向量、加了重排，可能有用，也可能只是把延迟搞大了。

**本项目做法**（`scripts/evaluate.py`）：
- **评估集**：100 道题，每题标注「正确片段所属文档 + 关键词」；分四组——基础概念（q01-q20）、语义改写（q21-q28）、进阶原理（q29-q62）、章节/干扰（q63-q100，其中 2 篇是无关文档），专门用来测向量检索、重排与防误召；
- **指标**：
  - `hit@1`：正确片段排第 1 的比例——最直观；
  - `hit@3`：排进前 3 的比例——反映「别漏」；
  - `MRR`：正确片段名次倒数的均值——综合排序质量；
- **四配置对比**：纯 BM25 / 混合 / 混合+重排 / 混合+改写+重排。

**实测结果**（14 个切片、100 题、bge-small-zh）：

| 配置 | hit@1 | hit@3 | MRR | 延迟 |
|---|---|---|---|---|
| 纯 BM25 | **0.72** | 0.93 | 0.818 | 3 ms |
| 混合召回 | 0.67 | 0.91 | 0.790 | 14 ms |
| 混合 + 重排 | 0.74 | 0.94 | 0.838 | 1.49 s |
| 混合 + 改写 + 重排 | **0.75** | **0.96** | **0.848** | 2.64 s |

**按题型拆开看（hit@1）**——这张表比总分更值得讲：

| 题目分组 | 题数 | 纯 BM25 | 混合召回 | 混合 + 重排 |
|---|---|---|---|---|
| 基础概念 q01-q20 | 20 | 0.70 | 0.65 | **0.80** |
| 语义改写 q21-q28 | 8 | 0.25 | **0.50** | **0.62** |
| 进阶原理 q29-q62 | 34 | **0.74** | 0.71 | 0.71 |
| 章节 / 干扰 q63-q100 | 38 | **0.82** | 0.68 | 0.76 |

**从数据里能读出什么**（面试加分项）：
1. 题目结构决定总分：62 题扩到 100 题后加入了更多章节题（问题几乎照抄标题/关键词），BM25 这类字面匹配近乎「开卷抄答案」，所以它能 0.82 领先——**评估集的偏置要先讲清楚，再谈模型强弱**；
2. 真正的价值在语义改写题：BM25 只有 0.25，混合召回翻倍到 0.50，重排再到 0.62——这组数字就是「为什么要做向量检索 + 重排」的量化证据；
3. 混合召回在章节题上反而掉到 0.68：RRF 融合会把一路的字面优势摊薄，说明「混合不是免费午餐」，权重/候选数要按场景调；
4. 延迟代价要写清楚：3ms → 2.6s，生产要缓存改写、只对候选做重排。本项目已实现 SQLite 缓存（TTL 1 小时）：同一批问题第二次平均 28ms，约 50 倍加速。

### 6.1 生成质量评估：检索对了 ≠ 答得好

检索指标只看「片段找没找到」，但用户看到的是答案。`scripts/evaluate_generation.py` 走完整 RAG 流程后，让裁判模型按 RAGAS 思路打分：

| 指标 | 含义 | 本项目实测（20 题） |
|---|---|---|
| 忠实度 faithfulness | 回答的每句话能否在引用原文找到依据（防幻觉） | 100 / 100 |
| 答案相关性 relevance | 是否正面、完整回答问题 | 99 / 100 |
| 引用质量 citation | 引用片段是否真的支撑回答 | 97 / 100 |
| 拒答 | 资料没讲时是否诚实说不知道 | 1 / 20 |

**两个必须知道的坑**：
1. 裁判要拿到**完整原文**，不能只给界面上的 160 字摘要——第一版用摘要当证据，分数只有 65/75/63，问题全出在「摘要没覆盖」被误判为「模型编造」；
2. 裁判和被评测是同一个模型 → 偏宽容，绝对分数只能看趋势，价值在横向对比（改 prompt / 换模型 / 开关重排），生产要换更强裁判 + 人工抽检。

### 6.2 向量索引：numpy 精确 vs FAISS HNSW 近似

- 几千块以内：numpy 矩阵乘一次就够，零依赖、结果精确（本项目默认）；
- 万级以上：每次查询 O(N·D) 会成为瓶颈 → FAISS HNSW，多层图近似最近邻，查询接近对数复杂度；
- HNSW 两个旋钮：`M`（每个节点连边数，越大越准越占内存）、`efSearch`（搜索宽度，越大越准越慢）；换来的是召回不是 100%；
- 本项目做成 `RAG_VECTOR_BACKEND=auto/numpy/faiss` + 创建失败自动降级：小库零依赖，大库可切换，同一检索接口两种实现——面试里讲「规模上来该换什么」比背参数更有用。

## 7. 降级与容错（面试常问）

| 故障 | 处理 |
|---|---|
| 向量模型加载失败 | 退化为哈希向量（`RAG_EMBED_BACKEND=hash`），服务不挂 |
| 某一路检索异常 | 退化为纯 BM25 |
| 重排输出不是合法 JSON | 保留原顺序 |
| 改写失败/超时 | 退回原问题 |
| MySQL 连不上 | 退化为 JSON 存储 |
| 缓存不可用 | 静默跳过（功能不变，只是每次都重新算） |
| cross 重排模型下载失败 | 自动回退 LLM 重排 |

**原则**：检索链路是「增强」，不是「依赖」——任何一层挂掉都要能退回到更简单的版本继续服务。

## 9. 面试问答（按本项目的真实实现准备）

**Q1：为什么用 RRF，不用加权求和？**
两路分数尺度不同（BM25 几十上百，余弦 0~1），加权求和要先归一化、还要调权重；RRF 只看名次，不用归一化，实现简单且稳健，k=60 是论文经验值。

**Q2：向量模型为什么选 bge-small-zh？**
中文优化、512 维、CPU 可跑、体积小；bge 系列查询侧建议加指令前缀，文档侧不加。换更大的模型（bge-m3）效果更好但更慢，本项目优先「任何人都能跑起来」。

**Q3：混合检索 hit@1 涨了但 hit@3 降了，怎么回事？**
混合召回把语义相关但词面不沾边的片段往前挪，个别题的正确答案被挤出前 3；说明融合权重/候选数还可以调，也说明单一指标不够，要看 hit@1、hit@3、MRR 一起。

**Q4：重排为什么用大模型打分，不用专门的 rerank 模型？**
项目已经有 DeepSeek Key，用 LLM 打分零额外依赖、能解释理由；专用 rerank 模型（如 bge-reranker）更快更便宜，是生产更常见的选择，项目留了接口。

**Q5：改写会不会引入噪声？**
会。所以兜底：改写失败/非法 JSON 退回原问题；且改写结果可缓存。另外评估集里专门有语义题，用它验证改写是否真的提升。

**Q6：怎么证明你的改动有效？**
评估集 28 题（含 8 道语义题）+ 四配置对比，指标 hit@1 / hit@3 / MRR + 延迟。数字写在 README 「检索评估」一节，别人可以复现。

**Q7：这套东西的瓶颈在哪？**
① 语料小（14 个切片），结论外推要谨慎；② 重排/改写都调大模型，延迟秒级；③ 内存索引，数据量大要换向量库；④ 评估集是人工标的，主观偏差。

**Q8：如果 QPS 上来会先崩哪里？**
先崩大模型调用（重排/改写/生成都调 API，有速率限制和成本）；其次是内存索引的全量扫描。应对：缓存（改写/答案）、重排只对候选做、检索和生成拆开扩容。
